## Review findings (most severe first)

**1. Generic event endpoint bypasses every M6 gate — posteriors and Mode 04 included.**
[routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:111) `post_event` accepts any `EVENT_TYPES` member. Probe (fresh L1/sim session, no ack): `POST /sessions/{id}/events {type:"test_result", payload:{test_id:"trim_idle_vs_2500", outcome:"lean_idle_normal_cruise", …}}` → 200, `tests_log` folded it and `vacuum_leak_post_maf` moved to 0.568 — no evaluator, no `safety_ack`, no runnable/already-performed check in [routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:197). Same endpoint accepted `codes_cleared` with a fake `token_sha256` (no token, no typed `CLEAR CODES`, no engine-off attestation, defeating [safety.py](/home/dreamz/mmc/backend/mmc/safety.py:239) and [routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:363)), plus `hypothesis_proposed`/`posterior_updated`/`llm_call` forgeries. This is the pre-M6 endpoint, but M6's "gates are code" claim rests on it. Fix: allowlist client-postable types (`safety_ack`, `observation_added`, `evidence_added`, `asr_segment`, `test_requested`) and reject engine/privileged types (`test_result`, `test_performed`, `posterior_updated`, `hypothesis_proposed`, `llm_call`, `sam_call`, `codes_clear_requested`, `codes_cleared`, `report_built`, `session_started`) with 403; add a regression test that the probe above returns 403 and leaves posteriors at priors.

**2. Replay sessions are writable through the core routes, so "read-only replay" is false.**
[runner.py](/home/dreamz/mmc/backend/mmc/replay/runner.py:3) promises replay sessions stay read-only; vision/upload routes enforce it ([routes_vision.py](/home/dreamz/mmc/backend/mmc/api/routes_vision.py:400)), but [routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:111) and [routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:197) do not. Probe on a `POST /replay` session: `POST …/events` (observation) → 200 and `POST …/tests/dtc_read/result` → 200, appending to the replay log and moving its posteriors; a following report then diverges from the bundle and, off-public with cached-LLM off, can spend Wonder money on a mutated replay. Fix: one `_require_writable()` guard (409 on `mode=="replay"`) on `post_event`, `post_test_result` and `upload_blob` in `routes.py`, mirroring the vision/upload guard; test that all three return 409 on a replay session.

**3. A bad Wonder reply kills the whole report (500, nothing saved), and the probability ban is porous.**
[wonder.py](/home/dreamz/mmc/backend/mmc/meta/wonder.py:156) `attach_review` catches only `BudgetExceeded`/`MetaClientError`/`NoCachedResponse`; probe: a banned-key reply raises `ValueError` out of `attach_review`, a schema-invalid reply raises `jsonschema.ValidationError` — neither is caught by the extra guard at [routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:427), so `POST …/report` 500s before `save_report`/`report_built`, contradicting "unavailable ships null, never blocks". Separately, `_scan_banned` is case-sensitive and [wonder_review.json](/home/dreamz/mmc/packages/schemas/wonder_review.json:1) has no `additionalProperties:false`: probe shows `{"Posterior":0.92,…}` and a narrative stating "92% certain" both pass scan+validation and are stored on the report. Fix: catch `ValueError` and `jsonschema.ValidationError` in `attach_review` (map to null + unavailable line), lower-case keys before the ban check, and set `additionalProperties:false` on the review and gap objects.

**4. Clear-codes never reaches the car: the backend token is unbound and unwired on Android.**
Backend mints a session-bound, hashed, 5-minute token ([safety.py](/home/dreamz/mmc/backend/mmc/safety.py:226)) and returns it as `clear_token` ([routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:386)), but no Android code calls `/clear-codes/*` (grep: zero call sites), and [ClearToken.kt](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/elm/ClearToken.kt:8) is a valueless local flag — any `ClearToken()` constructed in-process authorizes Mode 04 in [Allowlist.kt](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/elm/Allowlist.kt:49) with no backend value, expiry or session binding (only test code constructs one today, so Mode 04 is currently unreachable from the UI rather than exploitable). Fix: add the request/confirm calls to `SessionClient`, make `ClearToken` carry the backend token string + expiry + session id and have the driver reject expired/mismatched tokens; add an Android test that a locally-minted token is rejected.

**5. Web bundle upload is broken in the public (Modal) deployment.**
[Replay.tsx](/home/dreamz/mmc/web/src/pages/Replay.tsx:105) `uploadBundle` first creates a `mode:"sim"` session; [public.py](/home/dreamz/mmc/backend/mmc/public.py:110) rejects `sim` in public mode. Probe under `MMC_PUBLIC_MODE=replay`: that exact call → `400 public demo supports modes ['replay','upload']`. So the judge path advertised in [App.tsx](/home/dreamz/mmc/web/src/App.tsx:6) ("swap in a real Ford bundle by file drop") fails on the deployed site; the auto-fixture path works because it skips session creation. Fix: create the throwaway session as `mode:"upload"` (allowed publicly and locally), or add a session-less blob endpoint; add a public-mode test that drives the web sequence.

**6. Bundle replay loses the original session context and verifies no event chain.**
[runner.py](/home/dreamz/mmc/backend/mmc/replay/runner.py:53) `replay_bundle_bytes` always creates `user_level="L1", tools=[], vehicle=None` (the route body at [routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:137) has no level/tools fields at all), while `replay_session` preserves them — so a bundle recorded by an L3 tech with a multimeter replays with those tests blocked and different `next_tests`/`missing_evidence`. Posteriors survive (they don't depend on level/tools), which is why [test_replay_zero_spend.py](/home/dreamz/mmc/backend/tests/test_replay_zero_spend.py:33) passes vacuously: `sim-healthy.mmrec` contains a single slim `session_started` row and no test results, compared against an equally empty fresh session. Also, [mmrec.py](/home/dreamz/mmc/backend/mmc/replay/mmrec.py:82) only checks zip-member hashes against a self-consistent manifest; `_row_payload` discards `payload_sha256`/`prev_hash`/`hash` without verifying them — probe: a hand-crafted bundle with a fabricated gated `test_result` replayed to `vacuum_leak_post_maf` 0.568 under a fresh valid hash chain. Fix: persist `user_level`/`tools`/redacted vehicle in `meta.json` and restore them on bundle replay; verify the event hash chain when envelope fields are present; add a fixture with ≥2 real test results at L2+tools and assert full-state (not just posterior) equality.

**7. Report safety notes fabricate acknowledgements.**
[build.py](/home/dreamz/mmc/backend/mmc/report/build.py:183): `- {"none"}` binds tighter than `|`, so `"none"` survives, and the set is built from *available* next/blocked tests, not acked ones. Probe: a brand-new session with zero tests run reports `Safety gate acknowledged during session: engine_off / engine_running_outdoors / fuel_system / none.` — a false audit trail in a reproducibility-focused report. Fix: parenthesise the subtraction and derive gates from actual `safety_ack` events / performed gated tests in the log; test the empty-session report says no gates were acknowledged.

**8. Android Live screen one-tap ack defeats the checklist.**
[MmcApp.kt](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/ui/MmcApp.kt:1058) renders `Acknowledge safety: $gate` calling `ackGate()` directly — no ticks required — while the Test screen's `SafetyGateCard` correctly requires `allChecked`. A user can ack from Live, then Run, having seen no checklist items; the backend only ever sees the `safety_ack` event. (`SafetyGateCardTest` only exercises the pure helpers, so this ships green.) Relatedly, the card's offline fallback button at [MmcApp.kt](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/ui/MmcApp.kt:1154) calls `confirmGate`, which early-returns when `gateReady()` is false because items are empty — a permanent deadlock for any gate the backend doesn't serve a checklist for. Fix: route the Live button through `beginTest`/the checklist card (delete the direct `ackGate` button), and make the fallback ack explicit instead of gating it on `gateReady`.

**9. Concurrent test submissions double-count one test.**
[routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:204) checks `tests_log`/runnable from a `compute_state` snapshot, then awaits `_append_and_push` twice (each awaits a WS broadcast) before the `test_result` lands. Two concurrent submissions for the same test both pass the checks — `tests_log` only folds `test_result`, so even the first request's `test_performed` doesn't close the window — and both append, applying the same likelihood update twice. The EventStore lock makes each append atomic, not the check-then-append sequence. Fix: hold a per-session `asyncio.Lock` across check+appends in `post_test_result` (and the CSV `_submit_derived` loop), or re-check inside the registry append; test with two gathered concurrent posts expecting one 200 and one 409.

**10. Stop-and-see-a-pro over-fires on every body DTC.**
[safety.py](/home/dreamz/mmc/backend/mmc/safety.py:128) treats any `B*` code as SRS. Probe: `dtc_read` with `B1234` (a generic body code) produced "SRS code B1234 (airbag system…)" and, via [sessions.py](/home/dreamz/mmc/backend/mmc/sessions.py:380), emptied `next_tests` — a non-SRS body fault now halts all diagnosis with a pro referral. SPEC §8's trigger is an SRS/airbag fault, not the whole B range. Fix: restrict to known SRS DTC ranges/patterns (and keep the `safety:srs` user flag as the general path); test `B1234` does not trigger while an SRS-flag observation does.

**11. Repeated report builds re-spend Wonder; the "one call" test doesn't test the route.**
Each `POST …/report` builds a fresh report (`report_id=uuid4`, `wonder_review=None` at [build.py](/home/dreamz/mmc/backend/mmc/report/build.py:200)), so `attach_review`'s early-return at [wonder.py](/home/dreamz/mmc/backend/mmc/meta/wonder.py:164) never fires across builds; with `REPLAY_USE_CACHED_LLM=false` every rebuild is a new paid Wonder call (only the $120 tracker caps it). [test_report.py](/home/dreamz/mmc/backend/tests/test_report.py:190) reuses the *same* report object for the second attach, so it can't catch this. Fix: reuse a stored review for the session's current `log_head_hash` (or short-circuit when a `report_built` with a review already covers the head hash); add a route-level test with `replay_cached=False` asserting the second `POST …/report` makes zero transport calls.

**12. Level rendering leaks outcome slugs to L1 and mis-rounds natural frequencies.**
[levels.py](/home/dreamz/mmc/backend/mmc/levels.py:114) `trace_text` interpolates the raw KP outcome into L1: probe yields "One cylinder is misfiring: the 'p030n' result makes this more likely — Likely (about 7 in 10)." — the loader's jargon denylist never sees generated trace text. And [levels.py](/home/dreamz/mmc/backend/mmc/levels.py:98) uses Python's banker's `round`: `verbal_band(0.85)` → "Very likely (about 8 in 10)", `0.65` → "6 in 10", contradicting the adjacent band. Fix: map outcomes to plain-language phrases for L1 (or drop the slug from L1 text) and use `floor(p*10 + 0.5)`; add boundary tests at 0.85/0.65/0.25.

No non-Meta model, contributor ID, secret-in-log, or in-place history mutation was found in the M6 diff: Wonder/Spark pin checks, `call_record` redaction, hash-only clear-token logging, and engine-only posterior writes all hold as written. Focused tests I ran pass (`test_safety_gates.py`, Wonder rejection test), consistent with the gaps above being untested paths rather than red tests.
