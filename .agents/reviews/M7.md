Review of `git diff 1aa8fdf` (HEAD `ee24614`) plus the current uncommitted worktree. I ran the voice test files — 19 passed — and verified the findings below with targeted probes under `/tmp`. No repo files were edited.

**1. Critical — ASR finals are never persisted in production.**
[routes.py](/home/dreamz/mmc/backend/mmc/api/routes.py:654) defines `async def append_event`, but [voice.py](/home/dreamz/mmc/backend/mmc/meta/voice.py:277) calls `append_event(payload)` without awaiting it. The coroutine is discarded, so the `asr_segment` append and the state broadcast never execute. Probe with a route-style async append: nothing appended, `coroutine was never awaited` warning. Scenario: a real voice session transcribes, the user sees the final frame, but the event log contains no segment. All proxy tests inject synchronous append functions, so the suite stays green.
Fix: make the route append a plain function, or have `handle_final` await the result when it is awaitable. Add one test that passes an `async def` append through `AsrProxy.run`.

**2. Critical — Android voice is inert, and Confirm falsely claims success.**
[VoicePanel in MmcApp.kt](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/ui/MmcApp.kt:1092): "Hold to talk" only sets a status string. It never requests `RECORD_AUDIO`, captures audio, or opens a socket. [RealtimeAsrClient.kt](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/voice/RealtimeAsrClient.kt:20) is never instantiated anywhere in the app. Confirm at [MmcApp.kt:1114](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/ui/MmcApp.kt:1114) clears the pending intent and displays "Confirmed — logged through the test route" without any network call. Scenario: a user dictates "log 12.4 volts", taps Confirm, is told it logged, and no `test_result` event or posterior update ever happens. This fails the M7 acceptance behaviour while appearing to work. The JVM tests only cover parsing and TTS strings.
Fix: wire recorder → ASR socket → `VoiceUiState.onFinal`, and make Confirm call the existing test-result route with the staged measurement, showing success only on HTTP 200.

**3. High — the ASR budget guard can book $0 for paid audio.**
[voice.py](/home/dreamz/mmc/backend/mmc/meta/voice.py:134) returns `duration_s = 0.0` when the upstream final omits `audioProcessedMs`, and [handle_final](/home/dreamz/mmc/backend/mmc/meta/voice.py:271) checks `estimate_asr(duration_s or 1.0)` but then adds `estimate_asr(duration_s)` — i.e. $0. Probe confirmed spend stays `0.0`, and a textless `speechComplete` still appends an empty segment at $0. The proxy also never measures the PCM it forwards (48,000 bytes/s at `PCM_24KHZ`), so audio duration is entirely upstream-reported. This is the only paid path that can log cost 0; `MetaClient` falls back to the estimate in the same situation.
Fix: track forwarded bytes and elapsed time in `run()`, ledger the maximum of reported and measured duration per turn, and do not append or forward empty finals.

**4. High — the acceptance sweep reports PASS for failing suites.**
[acceptance_sweep.sh](/home/dreamz/mmc/scripts/acceptance_sweep.sh:18) greps the pytest tail for the word `passed`. A run ending `1 failed, 19 passed` satisfies every one of those checks, including the full-suite check at line 43. I verified both patterns in shell. The sweep is the M7 acceptance gate, so a red suite can produce a green sweep.
Fix: test pytest exit codes directly instead of grepping output text.

**5. High — the voice grammar can log 2500 as the measured value.**
[parse_number](/home/dreamz/mmc/backend/mmc/voice_commands.py:45) returns the first token that parses as a float, before any number-word parsing. Verified: `log cruise trim plus four at 2500` → `value: 2500.0`; `log voltage twelve volts and 2500 rpm` → `voltage_v: 2500.0`. After user confirmation this becomes a real `test_result` with a trim of +2500% or a 2500 V battery reading, moving posteriors on garbage. The Kotlin mirror diverges further: it sums all numeric tokens (2500 + the value) and lacks "sixty"–"ninety", which the backend accepts, so the pending card and the backend re-parse disagree despite the "single source of truth" claim.
Fix: exclude the `2500`/rpm tokens from value extraction and prefer the number adjacent to the unit. Share one fixture corpus between the Python and Kotlin parsers.

**6. Medium — concurrent report builds spend Wonder twice.**
[POST /report](/home/dreamz/mmc/backend/mmc/api/routes.py:526) performs the current-review check, the Wonder call, and the `report_built` append without the per-session lock that [post_test_result](/home/dreamz/mmc/backend/mmc/api/routes.py:334) correctly uses. Two simultaneous builds (double-click, judge retry, Modal's 32 concurrent inputs) both miss the stored review and both pay for a Wonder call, then append competing `report_built` events. This breaks the one-review-per-report rule.
Fix: hold `session_lock(session.id)` across check → build → append.

**7. Medium — stale Wonder reviews are resurrected after invalidation.**
When newer diagnostic events invalidate the stored review, [find_current_report_review](/home/dreamz/mmc/backend/mmc/sessions.py:506) correctly returns `None`, but the fallback at [routes.py:581](/home/dreamz/mmc/backend/mmc/api/routes.py:581) then serves [find_recorded_wonder_review](/home/dreamz/mmc/backend/mmc/sessions.py:486), which returns the latest review regardless of intervening events. Verified end-to-end: after a `safety_ack` following a recorded review, a keyless `POST /report` served the old review with `wonder_unavailable: None`. The report presents a senior review of a state that no longer exists.
Fix: reuse a recorded review only when the log head still matches that `report_built` event's recorded head, or when no diagnostic event follows it.

**8. Medium — blob-route session scoping is defeated by client-postable evidence.**
The download route at [routes.py:298](/home/dreamz/mmc/backend/mmc/api/routes.py:298) trusts any SHA named in the session's own `evidence_added` payloads, and `evidence_added` is client-postable at [routes.py:28](/home/dreamz/mmc/backend/mmc/api/routes.py:28) with no requirement that the session ever uploaded or was granted that blob. Verified: a second session posted a fabricated evidence record naming a victim session's manual-PDF SHA and downloaded the bytes with 200. The route's documented guarantee — unreferenced blobs stay unfetchable — fails on its own terms.
Fix: record blob ownership server-side at upload/vision time and serve only blobs that session actually produced or uploaded.

**9. Medium — first-touch session race can corrupt the hash chain.**
[SessionRegistry.get](/home/dreamz/mmc/backend/mmc/sessions.py:182) constructs and caches `EventStore` objects with no lock. Two concurrent first requests for the same stored session (routine after a Modal restart, with `max_inputs=32` on one container) each build an `EventStore` with its own cached `_next_seq`/`_head`; interleaved appends can then write duplicate seqs, fail on the SQLite primary key after the JSONL line is already written, and break `verify_chain()`.
Fix: guard `get`/create cache insertion with a registry lock so one `EventStore` exists per session path.

**10. Medium — blob upload reads the whole body before enforcing its size limit.**
[routes.py:237](/home/dreamz/mmc/backend/mmc/api/routes.py:237) does `data = await file.read()` and only then checks `MAX_BLOB_BYTES`. A multi-GB upload is fully buffered in the 1024 MB single Modal container before the 413 can fire, taking the judge site down for everyone.
Fix: stream in chunks and abort past 32 MB, or reject early on `Content-Length` plus a capped read.

**11. Medium — the proxy hangs after the upstream finishes.**
In [AsrProxy.run](/home/dreamz/mmc/backend/mmc/meta/voice.py:353), `pump.done()` is only checked after `client_ws.receive()` returns. When the upstream ends (the normal `PUSH_TO_TALK` completion) while the client holds the socket open, `run()` blocks indefinitely, the upstream close in `finally` never runs, and the next turn's PCM is sent to a dead upstream. The fake clients in the tests raise after the first final, hiding this.
Fix: race the client receive against pump completion (`asyncio.wait`, `FIRST_COMPLETED`).

**12. Low — the ASR model ID has no Meta/contributor guard.**
[voice.py:45](/home/dreamz/mmc/backend/mmc/meta/voice.py:45) takes `MODEL_ASR` from env verbatim and sends it upstream. `MetaClient` refuses contributor and non-Meta IDs at [client.py:122](/home/dreamz/mmc/backend/mmc/meta/client.py:122); the voice path bypasses that check entirely, so a `*-contributor` or foreign ID in env would be used and then echoed into session `model_pins` as if pinned.
Fix: apply the same `muse-voice-` prefix and contributor refusal when the proxy/factory starts.

**13. Low — the release `--check` verifies almost nothing about signing.**
[build_release_apk.sh](/home/dreamz/mmc/scripts/build_release_apk.sh:21) requires only that the keystore path exists and points outside the repo; the acceptance sweep passes it with an empty touched file. `MMC_KEYSTORE_PASSWORD`/`MMC_KEY_PASSWORD` are never required even though [build.gradle](/home/dreamz/mmc/android/app/build.gradle:34) reads them as signing passwords, so a real build fails late at Gradle instead of fast at the script. The post-build `apksigner verify` is optional and masked with `|| true`, and the private-key scan covers only the unstaged diff of two files.
Fix: require both password variables to be set, make `apksigner verify` mandatory and fatal, and scan staged plus untracked files.

**14. Low — demo-bundle transcripts encode misfire DTCs as a non-existent code.**
[make_demo_bundle.py:424](/home/dreamz/mmc/scripts/make_demo_bundle.py:424) hardcodes `"3033"` for any `P030x` code. Through the app's own decoder at [Parsers.kt:121](/home/dreamz/mmc/android/app/src/main/java/dev/dreamz/mmc/elm/Parsers.kt:121), bytes `30 33` decode to `P3033`, while the bundle's events record `P0303`. Any `ReplayTransport` playback of the coil demo shows a different DTC from the one the investigation folded.
Fix: emit the packed bytes for the actual code (`P0303` → `"0303"`).
